# TrueSee Architecture

This document describes the structure as of **Roadmap Phase 1 — Local Foundation** and the rules
later phases must follow. The governing document is the
[Constitution](./.specify/memory/constitution.md); where they differ, the Constitution wins.

## Repository layout

Two independent npm projects in one Git repository (owner decision D1). Each has its own
`package.json`, lockfile, lint/format/test configuration, and `.env.example`.

```text
TrueSee/
├── docker-compose.yml          # local PostgreSQL 18 (owner decision D2)
├── docker/postgres/init/       # creates the truesee_test database on first start
├── .github/workflows/ci.yml    # backend + mobile quality gate
├── TrueSeeBE/                  # NestJS backend
│   ├── prisma/                 # schema (no models yet) + migrations (baseline only)
│   ├── src/
│   │   ├── config/             # Zod-validated environment → AppConfigService
│   │   ├── logging/            # nestjs-pino setup, central redaction, request IDs
│   │   ├── database/           # PrismaService, startup connection check
│   │   ├── common/             # global exception filter, error codes
│   │   ├── health/             # GET /api/v1/health
│   │   ├── app.module.ts, app.setup.ts, main.ts
│   │   └── generated/prisma/   # generated client (git-ignored)
│   └── test/unit, test/integration
└── TrueSeeFE/                  # Expo app (development build, Android first)
    ├── App.tsx                 # composition root: wires config → client → use case → screen
    ├── src/domain/             # pure types and rules
    ├── src/application/        # use cases
    ├── src/infrastructure/     # config, HTTP clients (later: storage, sockets)
    ├── src/presentation/       # screens and components
    └── __tests__/              # mirrors src/
```

Native `android/` and `ios/` folders are generated by `expo prebuild` and are not committed.

## Mobile app: four layers

| Layer | May import | Must not import |
| --- | --- | --- |
| `domain` | nothing outside `domain` | React, React Native, Expo, `fetch`, storage |
| `application` | `domain` | presentation code, concrete infrastructure |
| `infrastructure` | `domain` | presentation code |
| `presentation` | `domain`, `application` types | concrete infrastructure (receives it via props/composition) |

Dependencies point inward toward `domain`. `App.tsx` is the only place that creates concrete
infrastructure objects and passes them in. Phase 1 example: `infrastructure/healthClient.ts`
produces a `HealthOutcome` (a domain type), `domain/connectionState.ts` maps it to a
`ConnectionState`, `application/checkBackendStatus.ts` adds single-flight behaviour, and
`presentation/AppShellScreen.tsx` renders it.

## Backend: modules

Phase 1 contains infrastructure modules only: `AppConfigModule`, `LoggingModule`,
`DatabaseModule`, `HealthModule`, plus a global exception filter. Controllers stay thin; logic
lives in services.

**Planned** (not present — each arrives in its own Roadmap Phase, one feature module per phase,
following [`prd.md`](./prd.md)): authentication and users starting in Phase 2, then the
messaging, media, and deepfake-related modules of later phases. Nothing from Phases 2–16 exists
in the code today.

The backend is an ES module project (`"type": "module"`), because NestJS 12 is published as ESM
only. Relative imports therefore use `.js` extensions, and Jest runs in native ESM mode.

## Data: source of truth

- **PostgreSQL is authoritative** for all server data. Schema changes happen only through Prisma
  migrations in `TrueSeeBE/prisma/migrations` (Phase 1: one empty baseline migration;
  `_prisma_migrations` is the only table).
- **Device storage** (offline cache, outbox) arrives in Roadmap Phase 8; until then the app holds
  no persistent data.
- Mobile configuration is public (`EXPO_PUBLIC_*` values are bundled into the app) and must never
  contain secrets.

## State management and navigation

| Concern | Chosen | Status |
| --- | --- | --- |
| Client state | Zustand (owner decision D3) | Not installed; added when the first shared state appears (Phase 2) |
| Navigation | Expo Router (owner decision D4) | Not installed; added when the second screen appears (Phase 2) |

## Conventions

### Errors

Every error response (except the liveness endpoint's 503) uses one envelope:

```json
{ "error": { "code": "NOT_FOUND", "message": "Route not found", "requestId": "<uuid>" } }
```

Clients branch on `code` only, never on `message`. Phase 1 codes: `NOT_FOUND`, `INTERNAL_ERROR`.
Unexpected errors never expose stack traces or internal details.

### Logging

- Structured pino logs: JSON (`LOG_FORMAT=json`, default in test/CI) or pretty (default in
  development) with the same content.
- Every line has `time` (ISO 8601 UTC), `level`, `msg`; request-scoped lines carry `reqId`.
- Request ID: a valid incoming `X-Request-Id` UUID is kept, otherwise a new UUID is generated;
  it is returned in the `X-Request-Id` response header and in error envelopes.
- Redaction is central (`TrueSeeBE/src/logging/redaction.ts`): `password`, `token`,
  `accessToken`, `refreshToken`, `authorization`, `cookie`, `set-cookie`, `secret`,
  `databaseUrl`, `DATABASE_URL` become `[REDACTED]`. The database URL is never logged; startup
  logs only `host:port/database`.
- Health-check requests log at `debug` level.

### Liveness endpoint rule (Constitution V, v1.0.1)

`GET /api/v1/health` is the only unauthenticated endpoint besides the future register, login, and
refresh endpoints. It performs no writes and returns only `{status, database}`:
`200 {"status":"ok","database":"up"}` or `503 {"status":"degraded","database":"down"}`, within
2 seconds (database check bounded by `HEALTH_DB_TIMEOUT_MS`). It never returns user data,
secrets, connection details, or version information.

### Configuration

Backend configuration is validated once at startup; invalid or missing values stop the process
with `CONFIG_INVALID` naming the variable. Every variable read by code is listed in the
corresponding `.env.example`.
